# Staff MFA (email one-time code) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let any staff member enable email-code MFA on their own account, require it to actually protect `cms_admin` sign-in once enabled, and let a `cms_admin` reset another staff member's MFA if they get locked out.

**Architecture:** Mount Better Auth's `twoFactor` plugin in `convex/auth.ts` configured for email OTP only (never TOTP/QR in the UI, even though the plugin generates a TOTP secret internally regardless). One shared client-side verification-step component is used by both sign-in entry points (`/staff-login` and the public `/sign-in`), since they share one Better Auth instance and either form can receive a `twoFactorRedirect` response. A new `cms_admin`-only Convex mutation reaches past the plugin's own session-scoped `disableTwoFactor` to clear another user's MFA state directly via the component's adapter, mirroring how `addStaffByEmail` already resolves users by identity.

**Tech Stack:** Better Auth's `twoFactor` plugin (`better-auth/plugins`) + `twoFactorClient` (`better-auth/client/plugins`), Convex, the existing Resend wiring from password reset (`convex/auth.ts`).

**Spec:** `docs/superpowers/specs/2026-11-03-staff-mfa-design.md`

## Global Constraints

- MFA is required (nagged, not blocked) only for `cms_admin`. `cms_editor` may enable it voluntarily; never nagged.
- Not hard-blocking: an unenrolled `cms_admin` still reaches `/admin`, with a persistent reminder.
- Never surface the TOTP `totpURI`/QR code anywhere in the UI — email OTP and backup codes only.
- **Known, accepted gap:** email delivery uses the same Resend sender as password reset (`onboarding@resend.dev`), which only delivers to the Resend account owner's own verified email (`sriharsha0413@gmail.com`) until a sending domain is verified. Every other `cms_admin` will be unable to complete sign-in once they enable MFA. Document this plainly (`documents/ARCHITECTURE.md`), and show it as warning copy on the enroll screen itself — but never block the enroll action on it (owner's explicit choice).
- `adminResetTwoFactor` refuses to target the caller's own row (owner-approved call from the design doc) — self-service disable is `disableTwoFactor`, which requires a password; this adapter-level path does not, so it must never be self-targetable.
- Server-side authorization only: every mutation/query re-checks role itself, same as every existing `cms:*`/`staff:*` boundary. UI gating (hidden nav, disabled banner) is never the security boundary.
- Match existing code style exactly: `catch (err) { setError(err instanceof Error ? err.message : "Something went wrong.") }` for mutation/client-auth error handling, native inputs/buttons styled like `account-auth-form.tsx`/`admin-staff-client.tsx` (no UI library), audit inserts shaped exactly like `content.ts`'s (`actorSubject`, `actorRole`, `action`, `resourceType`, `resourceId`, `metadata`, `createdAt`).
- No Convex-side or component test infrastructure exists in this repo (confirmed again for this plan — unchanged since the staff-management-ui plan). "Write the failing test" steps below are live-verification steps with an exact `Expected:` outcome instead, using the Convex CLI's `--identity` flag and the browser, same as that plan.

## Review Focus

- A `cms_admin` who enables MFA, then signs in again through the **public** `/sign-in` form instead of `/staff-login`, must still get the real verification step — not a silent false "you're signed in" state (today's actual bug on that form, found by this plan's own builder check: `authClient.signIn.email(...)`'s `twoFactorRedirect` response has no `error` field, so unchecked code treats it as success). Pinned by Task 4.
- Entering the wrong email-OTP code must fail clearly and let the user retry (within the plugin's own `allowedAttempts` limit), not silently "succeed" or crash the form. Pinned by Task 4.
- A `cms_editor` must never see the MFA reminder banner, and must never be nagged — only `cms_admin` without MFA enabled sees it. Pinned by Task 6.
- `adminResetTwoFactor` must be refused server-side for a `cms_editor` caller, for a self-targeted row, and for a target that has no MFA enrolled at all (no-op, not a crash) — not just hidden from a `cms_editor`'s UI. Pinned by Task 2.
- Completing enrollment (the OTP confirm step right after `enableTwoFactor`) must actually flip `user.twoFactorEnabled` to `true` — confirmed live against the real Better Auth state, not assumed from reading the plugin source alone, since this is the single fact the whole "reminder disappears" and "sign-in now requires a code" behavior depends on. Pinned by Task 3.

## Task 2: Backend — admin-reset mutation

**Files:**
- Modify: `convex/staff.ts`
- Test: live verification via the Convex CLI

**Interfaces:**
- Consumes: `requireStaff`, `extractBetterAuthUserId` (existing helper, `convex/staff.ts`), `createAuth` (existing import from `./auth`).
- Produces (for Task 6):
  - `api.staff.adminResetTwoFactor` mutation, args `{ id: Id<"staffMemberships"> }` → `{ reset: boolean }` (`false` if the target had no MFA enrolled — a no-op, not an error).

- [ ] **Step 1: Add `adminResetTwoFactor`**

```typescript
export const adminResetTwoFactor = mutation({
  args: { id: v.id("staffMemberships") },
  handler: async (ctx, args) => { /* ... */ },
});
```

Handler, in order:
1. `const staff = await requireStaff(ctx);` throw `"Only a CMS admin may reset another staff member's MFA."` if not `cms_admin`.
2. `const target = await ctx.db.get(args.id);` throw `"Staff record not found."` if missing.
3. Throw `"Cannot reset your own MFA this way — use the disable option on /admin/security instead."` if `target.authSubject === staff.authSubject`.
4. `const targetUserId = extractBetterAuthUserId(target.authSubject);`
5. `const authContext = await createAuth(ctx).$context;` (same access pattern `addStaffByEmail` already uses).
6. Delete the target's `twoFactor` row and capture the count: `const deletedCount = await authContext.adapter.deleteMany({ model: "twoFactor", where: [{ field: "userId", value: targetUserId }] });` (`DBAdapter.deleteMany` returns `Promise<number>`, confirmed from `@better-auth/core/dist/db/adapter/index.d.mts` — no separate `findOne` needed).
7. If `deletedCount > 0`: also `await authContext.adapter.update({ model: "user", where: [{ field: "id", value: targetUserId }], update: { twoFactorEnabled: false } });` and insert an `auditEvents` row (`action: "staff.mfaReset"`, `resourceType: "staffMemberships"`, `resourceId: args.id`, `metadata: {}`), return `{ reset: true }`.
8. If `deletedCount === 0`: return `{ reset: false }` with no audit insert (nothing changed).

- [ ] **Step 2: `npx tsc --noEmit` and `npm run lint` — both clean**

- [ ] **Step 3: Live-verify (this is the test for this task)**

With `npx convex dev` running: call `adminResetTwoFactor` via the CLI with `--identity` set to a `cms_editor`'s `tokenIdentifier` — expect the `cms_admin`-only rejection. Call it with a `cms_admin` identity targeting their own `staffMemberships` row id — expect the self-targeting rejection. Call it with a `cms_admin` identity targeting a staff row that has never enrolled MFA — expect `{ reset: false }`, no crash, no audit row inserted (confirm via `npx convex data auditEvents`). (Resetting a row that *has* enrolled MFA is re-verified end-to-end in Task 6, once enrollment exists to test against.)

- [ ] **Step 4: Commit**

```bash

git commit -m "feat(admin): add the cms_admin-only MFA reset mutation"
```
